# 假绿清单：那些「看着通过了、其实没检查」的形态

> 建立于 2026-11-02。起源是一天之内在同一类问题上栽了五次：**检查看起来在跑，
> 实际没检查到东西**。每一次的表象都是**全绿**。
>
> 这份清单不是忏悔录，是**判据手册**：下次写测试/守卫/验证脚本时，逐条对照。

## 为什么单独成文

散落在提交信息里的教训只能被当次提交的人看到。而这类错误的共同特征是
**它们不留下任何异常痕迹**——测试绿、门禁绿、日志干净。所以它们会被反复重犯，
每次都以为"这次测过了"。

## 八种形态（每条都有实测案例）

### 1. 尺子量错了对象

**案例**：`glyph_ink_probe` 用 `is_dark`（`R+G+B < 300`）判墨迹，
用来量彩色 emoji（📤 浅棕、📋 浅米，普遍 450+）⇒ 永远返回 0。

**判据**：先确认测量工具对被测对象**有区分力**。加一个「已知能过」的对照样本，
对照也失败就说明尺子坏了，不是被测对象坏了。

### 2. 验证手段本身没验证

**案例**：用 `timeout 25 cargo test …` 测「超时保护是否生效」。macOS **没有 `timeout`**，
rc=127，被 `$?` 读成 0 ⇒ 看起来通过。
另一例：`gate | tail -3 && git merge` —— pipeline 退出码取 `tail` 的 0，
门禁的红被吞掉，照常合并。

**判据**：
- 闸门必须捕获退出码（`out=$(...); rc=$?`），**不能接管道**
- 用外部命令前先确认它存在（`command -v`）
- 工具本身的行为要先测一遍

### 3. 断言看结果数据，而数据恒等

**案例**：「两条重复通知只该 read 一次」断言消息条数 == 3。但假 server 读后清空，
第二次 read 返回空 ⇒ 总数恒为 3 ⇒ **删掉去重逻辑测试也不红**。

**判据**：找**不随被测行为变化而恒等**的观测量。次数 > 结果，调用 > 产物，
状态迁移 > 终态快照。

### 4. 守卫覆盖面没跟上代码增长

**案例**：`check_script_modes.sh` 只扫 `gates.sh` / `ci.toml` 的裸路径调用（7 个），
新增的 `tools/channel-mcp-dir/*.sh` 不在数据源里 ⇒ 8 个文件是 100644 而门禁绿。
它们在**干净检出会 Permission denied**，但本地文件系统权限还在，怎么跑都绿。

**判据**：守卫的**数据源**会随仓库演化失效。要么定期用全局扫描兜底
（`git ls-files -s | awk '$1=="100644"'`），要么让判据基于「仓库自身约定」
（如同目录是否已有可执行兄弟）而不是硬编码清单。

### 5. 变异没打上 ≠ 守卫失效

**案例**：给「契约行必须在第一行」补样本后做变异，jq 里替换语法没生效，
结果 `pass=131 fail=0`——看起来像"守卫抓不住"。实际是变异根本没改到代码。

**判据**：`assert r != s` 不够（字符串替换可能"成功"但语义没变）。
要看**替换后的内容**确实不同，且最好是**语义相反**的变异
（`.[0]` → `.[-1]` 而不是换个写法）。

### 6. 判据的噪声底比信号还大

**案例**（2026-11-03）：想验「设置页里 mcp 的三个输入框真的画出来了」，
做法是渲染两次比像素差。三次尝试全部**恒真**：

| 做法 | 差异 | 把 mcp 条件块改成永不成立后 |
|---|---|---|
| 空列表 vs 有 mcp bot | 248 | **仍 248** |
| mcp bot vs dingtalk bot（两个窗口） | 18977 | **仍 18977** |
| 同一窗口切 selected | 19399 | **仍 19399** |

逐行诊断才看清：

```
y=150  diff=0
y=250  diff=2
y=350  diff=8
y=450  diff=0
```

**每行只有 0/2/8 个像素** —— 那 19399 是**累积的抗锯齿/渲染噪声**，
不是界面差异。想验的「多出三行字段」被噪声完全淹没。

**判据**：
- 先量**噪声底**（同一状态拍两次，看差异量）。信号必须**远高于**噪声底。
- 用**量级差异**而不是逐像素：数墨迹行数（6 行 vs 10 行）比数像素差稳得多。
- 一个实用的自检：**如果变异后数字一位都不变，那不是"守卫很强"，是判据在量噪声。**

### 7. 判据的分辨率不够（信号量级 ≈ 噪声）

**案例**（2026-11-03）：要给「体积闸必须在读文件之前」补测试，防止它退回
「先读完再判」。第一版判据是**耗时**：

```rust
assert!(elapsed < Duration::from_millis(20), "耗时过长 ⇒ 疑似先读了文件");
```

**变异逃逸了**：把读前那道闸去掉，测试照样过。因为 20 MB **稀疏文件**读起来
只要十几毫秒——信号的量级与噪声同档，判据分辨不出。

三次尝试：

| 判据 | 结果 |
|---|---|
| 耗时 < 20ms | **逃逸**（20MB 稀疏文件读太快，且依赖机器速度） |
| FIFO（读会阻塞） | **不通**（FIFO 的 `metadata().len()` 是 0，触发不了体积闸） |
| **源码守卫**（断言 `reject_if_too_big(meta_len)` 在 `fs::read` 之前） | ✅ 抓到 |

**判据**：
- 先估**信号的量级**与**噪声的量级**。同档就换判据，不要调阈值。
- 依赖机器速度、文件系统行为、执行顺序的判据都不稳；**能静态断言就不要动态测**。
- 自检：如果变异后数值只变化一点（不是数量级变化），那不是「守卫灵敏」，
  是**判据的分辨率不够**。

### 8. 改完没验证「改的行为」（不是判据错，是我没看）

**案例**（2026-11-03）：微信渠道的跨包 e2e（`abb_negotiates_real_wechat`）
要起 `crates/abb-channel-wechat` 的子进程。它硬编码了作者本机路径，
所以别处必然 `[skip]`。**同一张卡上我错了三次**：

| 次 | 我的说法 | 实际 |
|---|---|---|
| 1 | 三层寻址改好了 | 硬编码路径还在 |
| 2 | 门禁里真的跑了，数到 3 次 | 那 3 次是编译/测试名/结果行，**skip 时也有** |
| 3 | export 加上了 | **加在测试跑完之后**（`:193` vs `:142`） |

第 3 次由评审抓出，原话：

> `export ABB_WECHAT_BIN` 在 `tools/gates.sh:193`，而 root 测试在 `:142` 的
> `check_test_isolation.sh` 就跑完了 ⇒ 顺序反了，那条 e2e 一直 skip

**关键区别**：前七种是判据/尺子有问题；这一种是**改完之后没有验证「改的行为」**——
以为改了就是改对了，连"产物存在时会不会跳过"这种基本问题都没问。

**判据**：
- 改完**立刻**跑一次并**看输出**，不是看退出码（`ok` 在 skip 时也是 `ok`）
- 判据要挑**只有真执行才会出现**的观测量（本例改成测试真起子进程后才打印的
  `ABB_WECHAT_E2E_RAN`，有产物=1 / 无产物=0）
- **顺序敏感的东西（构建 → 传 env → 消费）要显式验行号**，别靠"我写在了后面所以应该没问题"

## 一个跨条的元判据

> **把被测行为改坏，测试必须变红。**

不红的断言等于不存在。这条听起来是常识，但上面**八条**全都是它被违反的具体方式。

配套做法：
- 每条守卫**都要**做一次变异验证（本仓 `tools/review-cadence/mutation-selftest.sh` 是范例）
- 变异要**双向**：改坏必须红，改回必须绿
- 变异后要**确认变异真的生效**（grep 替换标记 / 看编译是否重跑）
